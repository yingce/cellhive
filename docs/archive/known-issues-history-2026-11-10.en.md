# Known Issues and Release Status (Review Closure)

## 2026-11-08 ADR-311 canonical LTX migration (current)

The only production format now matches celld: owners use `cells/<scope>/own.json`; LTX uses `cells/<scope>/ltx/e<epoch>/<level-4hex>/<min>-<max>.ltx`. Readers and scans accept only canonical level directories and use continuation/offset listing. The old `owner.json`, `L1/`, decimal, `.snapshot`, `.batch`, and snapshot-started/done layouts are neither read nor produced. Complete snapshots are fsynced in a local spool and published once; COS contracts, 64 MiB paged restore, and the COS cold E2E all verified `missing=0 wrong=0`.

## 2026-11-05 ADR-309 Safe GC Operations and Cleanup Atomicity (In Progress, Not Deployed)

Adds an explicit admin/CLI Safe GC action (admin, scope and owner checks; dry-run), `KeepL1Generations` defaulting to two L1 generations, backlog/lag/L1-generation/deferred/retained-epoch metrics, and a deleting-fence plus idempotent cleanup job. Production remains DEFERRED and Safe is opt-in. The real HK COS 100k run exposed a cleanup 502 leaving e1/e2 fully deleted and e3 half deleted; no online-GC safety claim is made before acceptance.

## 2026-11-05 ADR-308 Restore Lower Bound and Safe Deletion (In Progress, Not Deployed)

Restore now enforces marker cuts as a lower bound, monotonic cuts, cut-before-prune, full page coverage for no-L1 snapshots, and skips `gc-retired` epochs. Read paths retry a transient `ErrNotFound` after re-reading the manifest/chain, otherwise fail closed. Safe deletion adds leased reader pins, an immutable epoch seal with drain, per-key tombstones with a grace period, and explicit `RetireOptions.Safe`; the production default remains DEFERRED and background work must not enable Safe. Multi-epoch owner-switch and large-data tests are local evidence only; no deployment or full online-GC claim.

## 2026-11-04 Replication GC Safety (ADR-307, Contract First, In Progress, Not Deployed)

Final epoch review cannot prove atomic owner validation across objects or pinned-reader/lineage-cut safety. Compaction keeps publishing, but physical covered-L0/old-L1/`RetireEpochs` payload deletion defaults to DEFERRED. `Options.GC` is intent only; explicit `OfflineQuiescent bool` defaults to `false` and requires externally quiesced writers AND readers throughout deletion. Production background never opts in; intervals cannot bypass. Absent owner/nil `Verify` are not permission. Configured per-delete `Verify` stops observed loss, not the race; optional payload ETag cannot prove ownership.

Preserve marker/link/epoch-cut/snapshot-started/done/unknown names in all modes; report `ReportDeferredGC`/`GCSkipped` deterministically without claiming unperformed deletion succeeded. Immutable epoch-cut, complete manifest/index proof, cut-before-prune and durable large-marker-before-Serve fixes are in implementation and acceptance, not unchanged and not fully accepted. No pending-deletion registry; bundle/assets ops GC unchanged. Bucket growth and historical List costs remain; generation descriptors, monotonic epoch references and reader pinning for full online GC are unresolved. This status supersedes the older unchanged-defects wording and deletion implications below; ADR-306 local acceptance does not validate ADR-307 or deployment.

## 2026-11-04 Performance Batch (Incremental Local Acceptance, Uncommitted, Not Deployed)

See the [current authoritative status](../known-issues.md) and ADR-306. Stable source changes include canonical covered-snapshot skips, zero-L0-only MinBytes early exit, index-watermark-guarded covered-L0 GC, a 5m per-scope compaction deadline, 512MiB object reads, 64MiB supervisor blob/segment limits and explicit oversized-blob 413. Default peer/HTTPStore total deadlines are 30s/60s; slow large transfers can still fail.

Read/dispatch projections share a 5s TTL, while all mutators use `projectionStrict` and do not inherit stale configuration. Owner atomic read fences and `cacheEpoch` prevent a trim from turning `0==0` into a valid stale read. Invocation retention is a soft 7-day/10000-row target, write-triggered at 1 minute or 256 writes with up to 1000 rows per age/count cleanup query. Timer indexes remain; post-commit fresh `syncIndex` was restored for pre-Put crash safety, and removing that reconciliation was reverted. Go logbuf has separate 1MiB entry/event budgets per worker, with bounded message/args/exceptions; rejected records do not consume seq and eviction is observability retention loss, not business failure.

Incremental review ACCEPTed the four introduced blockers: native facet/version Maps restored, timer post-commit fresh index synchronization restored, owner atomic fence/cache epoch protection restored, and strict projection used by all mutators. Local verification reported Node 141/141, full Go, vet, timer/owner race, focused server, and real pinned user-runtime/do-runtime passes. This is not the earlier 134-Node result and is not GA, production acceptance, or deployment.

JS response streaming covers workerd hops only; the Go DO proxy still buffers up to 8.25MiB. DO seen uses CountLRU(10000), native facet/version identity remains in Maps; the prior unbounded Map memory optimization was withdrawn as preexisting behavior. The 65MiB source-cache budget is not an admission limit: valid UTF-16-weight oversized sources bypass caching and remain accepted, so cache thrash is not fixed. Full restore memory/streaming, old-epoch GC cost, complete Range/background timeout coverage, and slow-link risks remain. The six confirmed user-raised epoch/lineage protocol defects remain unchanged release gates. Existing narrow failed-delete/concurrent-publish behavior is preexisting, not introduced by this batch. No commit or deployment.

## 2026-10-24 COS cell latency, restore, and Cron recovery (ADR-276–278)

The KV/Queue resource deletion fence now uses a stable point-read key instead of repeatedly reading an absent segmented authority key that caused a bucket List on each write. Restore retains an epoch whose L0 was fully compacted into L1; initial snapshot start/done markers use the same committed watermark. A 180-second real-COS five-scenario run recovered all 140 acknowledged keys with `missing=0`, `wrong=0`, and SQLite `integrity_check=ok`. Its steady put p99 was 511.8ms (GET p99 65.3ms), restart first write 3874ms, and cold-restore first write 4183ms. **The design latency targets remain unmet**; the E2E script's PASS used a relaxed 10-second limit to complete integrity checks. Measurements and limits are recorded in [the COS benchmark](bench/cold-write-fence-v2-2026-10-24.md).

Cron uses its own `__cron__` cell and does not directly read the KV/Queue resource fence. A pinned-workerd Docker E2E confirmed both expressions advanced to a new minute without duplicate slots after cell-agent SIGKILL/restart. This does not cover a whole minute missed during downtime: CellHive schedules the current minute best-effort and does not backfill. celld instead persists an alarm in its cron cell and can execute one overdue occurrence after downtime. Shared node-lease, COS, or control-plane contention can still indirectly delay Cron.

ADR-281 addresses an SG timer that kept returning HTTP 400 after `vwork-24/kv-cache-counter` removed its Cron trigger: the persisted slot had no dispatch identity because the active version's `Crons` was empty. Already materialized slots now resolve the active worker and retain their original Cron expression; a missing worker or unavailable control projection remains retryable without sending an invalid request. After rollout, live handler verification is still required. An earlier tenant handler failure (`VWORK runtime context is invalid`) remains a separate possible cause of retries.

ADR-279 reuses the physical authority windows already returned by a node-lease listing. A real-COS probe listed three historical nodes with one List; a subsequent 180-second sequential run reduced global steady Lists from 1243 to 421 and measured put p99 450.7ms, GET p99 56.1ms, restart first write 3893ms, and cold first write 2868ms. All 140 acknowledged keys survived, but the write, restart, and cold-restore latency targets remain unmet. A cancelled compaction left almost 1000 segments before restart, contributing to restore work; the existing restore concurrency limit protects against prior mass-hydrate OOM and must not be raised without a global resource bound.

## C-05 DO Alarm Recovery (Finalized)

1. alarm rows are replicated to cell-agent with the actor SQLite (durable).
2. **supervisor only reads workerd's alarm table and extracts due times**, then reports to cell-agent: `alarm_upsert(scope, dueAt, token)` / `alarm_delete(scope, token)`.
3. cell-agent maintains the due index in the **waker cell** (bucketed by time).
4. When waker finds an item whose "owner is dead + due", it **targets takeover of that DO** (claim + restore) to an available do-runtime. The new owner reads the alarm row and dispatches it; after successful dispatch, it atomically advances/deletes the index item.
5. **DOs with alarms are prioritized for residency** (placement policy / similar to `DO_PREVENT_EVICTION`) to reduce cold activation.
6. If the alarm table cannot be reliably extracted (P0 schema validation), fall back: waker periodically queries live supervisors for their earliest due alarm, and only performs takeover for owners that are dead.

## I-01 Tenant Binding Authorization (Finalized)

- **The primary line of defense is network isolation** (see I-09): tenant Workers **cannot** access internal cell-agent :7001.
- Platform role tokens **exist only between the host adapter (platform code) and cell-agent** and are **never injected into tenant env**; tenants receive only binding facades.
- The host adapter generates a resource-scoped token for each binding; cell-agent validates its signature, namespace, binding kind/name, and registered ACL, rejecting missing or elevated access (ADR-074/181).
- ADR-304 requires stateless kid pattern ceilings, fixed maximum86400 seconds, expiry/root rotation, no issuer registry or instant revocation; amendment implementation and acceptance are in progress. See [`security.md`](../en/security.md).
- Management/business bindings use Bearer HS256 JWT; namespace business authority is separate from platform admin, with no static/OIDC fallback.

## I-03 WAL Checkpoint/Truncation (Finalized)

- supervisor polls `(salt, frame)`; salt changes or frame resets to zero = checkpoint occurred.
- On detection → **pause the delta stream** → use the **SQLite Online Backup API** (read-only connection) to take a consistent snapshot → upload it as an **L9 snapshot** (temporary key + atomic commit) and record txid → resume delta from the new salt/frame 0, and write the **snapshot→delta handoff marker**.
- cell-agent validates snapshot integrity and handoff continuity.
- P0 must test: detection and alignment when a checkpoint is triggered **during active writes**.

## I-04 DO WebSocket Semantics (Finalized, CF-compatible)

- **Deployment / promote / migration all restart the DO**: the old owner closes WS with **1012**; **the client reconnects**; the new owner reconstructs, and **the handler restarts** (`webSocketOpen` is triggered again).
- **No resume**: the platform does not guarantee session continuity across restarts; DO session state must be persisted to storage.
- The host adapter is only responsible for: detecting disconnect → resolving the owner again → having the client reconnect.
- Consistent with Cloudflare behavior (ADR-032).

## I-05 Timer Dispatch Deduplication (Finalized)

- Deduplication is on the **cell side**: the timer carries `token = hash(scope, kind, dueAt, occurrence)`; cell SQLite records `fired:<token>` (TTL).
- **Tokens already fired are skipped**; cron triggers once per slot unique key; DO alarm is based on the alarm row in actor SQLite, and after successful dispatch the due index is atomically advanced/deleted.
- user-runtime **does not perform deduplication** (stateless).

## I-07 scope-hash Routing (Finalized)

- The hash is only **best-effort affinity (performance hint)**, not a hard constraint.
- If the preferred cell-agent is unavailable → **switch to the next available node**; segments uploaded by different nodes are merged by **epoch prefix** without ambiguity; the owner record is authoritative.
- An optional consistent hashing ring can reduce churn when membership changes.

## I-09 Multi-tenant Isolation (Finalized)

- workerd capnp: `globalOutbound` of a tenant loaded worker = **public-Internet-only network service** (excluding RFC1918 / cell-agent addresses).
- **The host adapter's internal-network binding is not exposed to tenants**.
- Per-worker CPU time and V8 heap enforcement are **not implemented**; subrequest limits are enforced by the dynamic Worker invocation quota and covered by a real workerd test. Current additional controls are deploy-time WorkerCode/env budgets, per-namespace write admission, and cell-agent overload rejection. See [`security.md`](../en/security.md).
- **Dynamic-load aggregate memory protection is still being closed out (measured 2026-10-13)**: earlier pinned-workerd tests in a 2 GiB container were OOMKilled after 451 distinct 1 MiB Workers or 575 same-SHA versions; 189 distinct 10 MiB assets also triggered OOM. Public user-runtime now has version retirement, activity lifetime tracking, cold-load admission, byte budgets for source/plan/env/assets, and streaming for large assets; the same 2 GiB/1000×1 MiB synthetic Worker run no longer OOMKilled, but still observed roughly 840 MiB cgroup usage and workerd abort logs, so this is not a production capacity guarantee. DO runtime, internal dispatch, long-lived RPC/WS, FD limits, and long churn remain separate validation work. Evidence: [`runtime-memory-2026-10-13.md`](bench/runtime-memory-2026-10-13.md) and [`workerd-loader-lifecycle-2026-10-13.md`](bench/workerd-loader-lifecycle-2026-10-13.md).

## M-10 Rate Limiting/Quota/Admission (admission implemented, ADR-087)

- per-namespace write rate limiting; cell-agent returns `503 overloaded` when overloaded.

## purge / uploads / WAL / r2.List (updates after ADR-134)

- **Delete/purge**: soft delete + `purges` jobs + `RunPurgeLoop` have landed (ADR-131), and purge only applies to entities that are **still in soft-deleted state**; deploy/create cancels the job (ADR-135); **data-side hook is wired (ADR-142)**: worker deletion removes that worker’s DO segments and assets, app deletion removes the entire namespace’s `cells/`+`assets/`, every cell-agent executes it (cross-node local replica drain + bucket deletion are idempotent), and the hook is resumable (bounded deletes per pass, `done=false` keeps it pending). **Completed (ADR-169)**: data side switched to `objectstore.Objects.ListPage` + `bucket.PagedLister` cursor-paginated deletion (S3 `StartAfter`; bounded memory); `Purger.delete` advances while deleting, and the next pass resumes when the budget is exhausted. **Remaining**: each pass rescans from the target prefix start (no cross-pass persisted cursor; cold path); FS dev still walks the tree per page (bounded memory).
- **async bucket uploads**: a **persistent retry queue** exists (ADR-143): pre-write spool (`<DATA_DIR>/upload-spool`) + startup/periodic replay; failures count as `deferred` (only a persistence failure combined with upload failure is `dropped`), and `/metrics` exposes spool/deferred/dropped. **Completed (ADR-171)**: atomic spool publish (tmp fsync → rename → leaf-directory fsync on every mutation; parent-directory creation is memoized per process), plus leaf-directory fsync after successful `Remove`, making both publication and completion power-loss durable.
- **Authority bucket compatibility**: S3 `ConditionalDelete` relies on `DeleteObject If-Match`; ignoring it could erase a newer owner/lease, so `cell-agent` exits on any failed startup probe. `CELLHIVE_BUCKET` accepts empty (local), `s3://`, and native append-backed `oss://` / `cos://`; other schemes fail closed. Native providers use `AppendObject(position)` and tombstone frames for mutable authority CAS/delete, never a non-atomic `HEAD+PUT/DELETE` substitute. On 2026-09-22, isolated concurrent claims, CAS/conditional delete, and startup diagnose passed on the OSS Beijing bucket and COS Hong Kong `cell-1376795072` bucket; same-host dual-process `SIGKILL`/fresh-directory takeover against each real cloud bucket and high-concurrency exact-value checks also passed (ADR-189). ## Deletion/Cleanup (ADR-131/142, implemented)

Deletion is **two-phase**: the request path only performs control-plane soft delete (revocation + audit); data cleanup is completed by an idempotent, rerunnable, paginated purge loop:

1. `DELETE /v1/control/worker|app` soft-deletes in the same transaction and writes `purges(ns, worker, state, requested_ms, attempts, last_error)` via `enqueuePurgeTx`; worker/app immediately becomes unroutable.
2. cell-agent’s `RunPurgeLoop` (default 5s tick, up to 20 `PendingPurges` per pass) calls `Purger.Run(ns, worker)`: `MaxDeletes` (default 500) cleans bucket prefixes `cells/<ns>/`, `assets/<ns>/` in a **bounded** way; `worker==""` (app-level) cleans **all resources + DO storage**, otherwise it only cleans that worker’s **DO storage (`cells/<ns>/__do__/…`) and its assets** (KV/D1/R2/Queue resources survive across workers, same as CF). If not fully cleaned, it returns `done=false` and the job remains for the next tick; failures call `FailPurge` to record attempts/last_error and then retry; completion calls `FinishPurge` to delete the job + audit.
3. Redeploy cancels pending purge **in the same transaction**, and purge skips workers/apps already `resurrected` when it runs (`TestPurgeSkipsResurrectedWorker`/`App`).
4. Local replicas are handled by each owner (`LocalCells.DeleteNamespace`/`ForgetPrefix`).

Tests: `internal/purge TestAppPurgeDropsNamespaceData`/`TestWorkerPurgeDropsOnlyThatWorker`, `internal/control TestPurgeSkipsResurrectedWorker`/`App`/`TestRunPurgeLoopResumableHook`, `internal/server TestWorkerDeletePurgesAssets`.

## Benchmark Environment Limitations (Not Defects, Need to Know)

- The local **FS bucket uses a single global mutex** (`internal/bucket/fsbucket.go`) to serialize `Put/CAS/List`, and shares the same disk with SQLite → **multiple cells do not add up when capture is ON** (FS single ~5.4k, dual ~8k peak ≈1.47x; local MinIO dual-cell has no gain). Near-linear scaling is only possible in production with real distributed object storage + separate disks.
- The upload layer is already sharded by scope (`upload.NewSharded`, order-preserving), but sharding is not useful when sink parallelism is insufficient.
- The single-cell write ceiling is limited by "one commit proof round trip per write"; throughput is limited by the single writer and "one proof per write" (peak CPU only ~2/8 cores).
