# CellHive hotfix 20261031-03

Source: `c9ba0fd` (`fix(user-runtime): do not retry successful dispatch when
invocation logging fails`).
Image: `sgccr.ccs.tencentyun.com/vwork/cellhive:20261031-03`
Digest: `sha256:f3a7cf6b1e515e8a94e205f9dc89fa70f2d9d615b7e28d536e885d07b6022159`.

## Change

`dispatchTimers`, `dispatchQueues` and `dispatchWorkflows` called
`finishInvocation` inside the handler try block. A 503 from the invocation store
after `handleScheduled`/`handleQueue`/`handleWorkflow` had already succeeded was
rethrown as `handler_failed`, so cell-agent retried and re-ran side effects.

Invocation persistence is now best-effort on the finish path: the error is
logged but the handler result is returned. `startInvocation` still gates
execution (queue dedupe needs the record), and real handler errors still return
500. Regression test: scheduled() succeeds while the finish POST returns 503;
dispatch must return 200.

## Why this did not stop the vlog cron

`vwork-40/vlog-daily-report` (cron `30 3 * * *`) is a tenant-side failure, not
an invocation-logging failure. A manual dispatch returned:

```json
{
  "error": "handler_failed",
  "message": "Error: Feishu send failed with HTTP 200",
  "invocation_id": "018aabe6-592b-4432-91e7-80283474f44d"
}
```

The bundle's `sendFeishu` throws when the webhook responds HTTP 200 but
`payload.code ?? payload.StatusCode` is non-zero or missing/non-JSON. The
scheduled handler therefore throws on every attempt; cell-agent's retry is
working as designed and continues (attempts reached 303) until the tenant
function is fixed or the cron is paused. The platform hotfix only prevents a
*different* failure mode (successful handler + failed invocation logging).

Separately, `vwork-40/__invocations__/main` still has no recent records; that
is an invocation-store/ownership issue and does not cause this 500.
