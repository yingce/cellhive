## 已确认的放大链

1. **节点续租不是只有一次写。** 默认 TTL 10 秒，`runNodeLeaseRenewal` 约每 TTL/3 续租（计入执行耗时，日志约 3.4 秒）。`lease.Publish → SegmentedAuthority.CAS → latest → mutate`：读根 → 读当前分段 → 再校验根 → Append → 写后校验根。两台 agent 都捕获到一次正常续租包含 **4 GET + 1 Append**。示例 agent-0 request 2249–2253，17:22:50.466–50.589 UTC；agent-1 request 6617–6621，17:26:43.646 起。路径分别为节点 `.json` 和 `.json.g11`。这部分约为双节点 2.3–2.4 GET/s，实际有扫描/刷新重合与耗时波动。
2. **peer 刷新持续读桶。** `RunKnownRefresh → refreshKnown → Get` 默认每 2 秒检查已知 peer；新鲜观察可复用，未覆盖时仍点查。暖读为分段 + 根校验两个 GET。agent-0 对 agent-1 两个路径的间隔中位数约 2 秒。另外 full discovery 的 List 解析也会读 lease；SG lease/list 本窗口 0.666/s。
3. **Recovery 即使没有死节点也选主。** `Runner.Run(5s) → Pass → IsLeader → Election.Acquire` 在发现候选之前执行。两个 agent 都检查 `fleet/waker.json`。正常 leader 的 holder 暖读 2 GET + CAS 的 4 GET，非 leader holder 暖读 2 GET，每 5 秒合计约 8 GET，即 **1.6/s**；指标分别为 SG 1.598、USW 1.591、GZ 1.595/s，日志 follower 的分段/根读取间隔约 5 秒。Recovery 剩余主要为节点 lease 点查，历史 sealed session 过滤已经生效。
4. **Cron/Timer 是多阶段读。** SG cron_plan 2.098、cron_dispatch 1.324、timer 1.240、cron_retry 0.832/s。每轮控制 owner 校验、任务 cell owner 校验与 wake 更新叠加，权威暖读通常再乘 2。多个不同后台循环各自验证控制 owner，控制 cell 驻留并不会消除这些 COS 校验。源码 `internal/cron/scheduler.go`、`cmd/cell-agent/main.go`、control read 路径与指标一致；不把共享路径的每条日志强行分配到某个任务。
5. **wake 的兼容清理仍点查旧路径。** `wake.Index.Put/Delete` 调用 `candidate(legacyKey(scope))`；即使不存在旧 `wake/<scope>.json` 也发 GET。已保留日志可见多个 Cron 的旧路径反复 404。它不一定是失败重试，而是每次正常更新/删除的兼容检查；指针不存在也会有 404。不能仅因 404 就关闭恢复扫描。

协议倍增来自现行 authority reclaim 的 root 校验，用于防止被删除的旧 generation 被迟到写重建后误当当前值。不得直接删校验或回退 legacy 模式来降低 GET。

## 后续优化顺序（本次未实施）

- 优先减少 Recovery 和 waker 对同一选主状态的重复获取/续约，定义共享已确认租约证明与到期/换主失效，保留真正接管时的权威检查。
- 在同一任务/批次复用合法 owner 校验结果，合并控制面维护与 peer lease 观察；不得把跨请求旧值无条件当权威。
- 为 wake 旧格式兼容明确迁移完成/旧写者隔离边界，再去掉每次更新的旧路径 404；单次 404 不能证明以后无旧写入。
- 更大幅降低续租本身的 GET 需要单独审查 authority CAS 协议，不能只延长 TTL 或删 root 校验。
