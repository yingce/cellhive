# Runtime 502 local regression — 2026-11-11

## Root cause and implementation

The old production image reproduced HTTP 502/503 locally: 22/4400 failures at concurrency 8 and 183/4730 at concurrency 32. Captured evidence showed two independent faults: unconsumed invocation-log HTTP response bodies accumulated sockets until the workerd child reached its 1024 soft fd limit; continuously-ready event-loop work could defer polling new health connections for multiple seconds, triggering watchdog termination even while business requests succeeded.

The loader now consumes both OTLP and fallback log response bodies, and the span exporter consumes its response. Workerd CLI uses a bounded busy-poll interval of 64 events. Watchdog failures close admission and wait for active requests, bounded by DrainGrace (30 seconds by default), before terminating the unhealthy generation. This is not automatic business request replay. Health probes drain their small response body for connection reuse. The release build script invokes the optimized build rather than trusting an arbitrary bazel-bin artifact.

## Non-blocking telemetry follow-up

Invocation logs and platform spans now share per-isolate export admission (16 concurrent requests), without a waiting queue. Excess best-effort telemetry is dropped; business storage operations are unaffected. Every accepted export has a 3-second deadline covering headers and body, drains successful responses without retaining them, and cancels responses over 64 KiB. Invocation logging and span export remain in waitUntil; neither the business response nor the resident lease waits for completion. OTLP failure may fall back to the agent, under the same per-isolate export limit.

A cold-start test uncovered a separate 503: concurrent requests joining preparedInflight were each counted as a new cold load. They now share one admission per immutable worker version. The limit of 16 distinct concurrent preparations remains. A regression with 64 callers of one version plus 15 distinct versions validates coalescing and overflow rejection.

Targeted JS tests: 30/30. The full JS target plus runtime and DO integration packages passed before the final cold-count change; all loader JS tests and the combined targeted suite passed after that change.

Real fault-injection evidence: fault-results.jsonl, fault-fds.jsonl and fault-runtime.log in the evidence directory. The first run reproduced cold-load 503 and is retained under before-cold-admission-fix. A later harness run began before runtime readiness and recorded transport resets; preserved under before-readiness-gate. The final harness waits for health only (no business warm-up), then sends 32 concurrent cold requests and tests healthy/headers-hung/body-hung/reset/503/recovered collectors, 15 seconds each. Results are appended below after completion.

Local-file-to-Vector export was discussed as a subsequent alternative, not implemented or deployed in this change. Current USW Vector source was verified to be opentelemetry; a file design requires durable rotating files, asynchronous bounded writing, per-node collection and saved offsets. Existing per-slot workerd.log is deleted on process cleanup and must not be mistaken for a durable spool.
